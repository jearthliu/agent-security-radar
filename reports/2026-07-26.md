# Agent Security Radar — 2026-07-26

## Window and method

- Window: 2026-07-19 through 2026-07-26, China Standard Time
- Selection: exactly five non-duplicate papers with direct arXiv sources
- Mapping: finding → lifecycle stage → risk → engineering control
- Evidence rule: numerical results below are author-reported and have not been independently reproduced for this radar

## 1. Cryptographically verifiable authorization for autonomous agents

**Paper:** [Toward cryptographically verifiable authorization for autonomous AI agents](https://arxiv.org/abs/2607.21325)  
**Submitted:** 2026-07-23  
**Stage:** Authorization → Execution

**Fact.** The paper proposes Cryptographically Verifiable Agent Authorization, binding an agent principal, concrete request, execution context, and policy satisfaction. It presents candidate security properties and a Groth16 zk-SNARK proof of concept.

**Why it matters.** Agent identity alone does not prove that a particular request was authorized under the current policy and context.

**Engineering interpretation.** Consequential tool calls should carry action-specific, context-bound authorization evidence with replay resistance. Identity, request authorization, and runtime execution binding should be modeled separately.

**Unknown.** This is described as a security hypothesis and preliminary model. Production performance, policy expressiveness, revocation, and operational key management remain open.

## 2. Malicious issue requests against coding agents

**Paper:** [IssueTrojanBench: Benchmarking AI Coding Agents Against Malicious Issue Requests](https://arxiv.org/abs/2607.20759)  
**Submitted:** 2026-07-22  
**Stage:** Untrusted input → Planning → Tool execution

**Fact.** IssueTrojanBench evaluates malicious instructions delivered through software-development issues and related artifacts against several deployed coding-agent configurations. The authors report that 66.5% of benchmark issues penetrated the evaluated guardrails.

**Why it matters.** An issue, comment, PDF, or repository file is data supplied by another party, but a coding agent may interpret it as authority to read files, execute code, or call external APIs.

**Engineering interpretation.** Coding agents need provenance labels, capability isolation, explicit confirmation for consequential actions, and policy enforcement outside the model. Issue content must never grant itself authority.

**Unknown.** The reported rate is specific to the benchmark, models, agent versions, and configurations tested. Independent replication and longitudinal results across updated defenses are still needed.

## 3. Internal geometry of perturbed jailbreak prompts

**Paper:** [Geometric Configurations of Perturbed Jailbreak Prompts](https://arxiv.org/abs/2607.20581)  
**Submitted:** 2026-07-22  
**Stage:** Input → Model response

**Fact.** The authors analyze perturbed jailbreak prompts in selected Qwen and Llama small-weight models using embedding and next-token probability spaces. They report no general behavioral hyperplane in the refusal-dominated answer set they studied.

**Why it matters.** Simple assumptions that harmful and safe prompts occupy a cleanly separable internal region may not support robust runtime defenses.

**Engineering interpretation.** Do not rely on a single latent-space classifier or spelling-based detector. Combine input controls with capability restriction, output validation, and action-level policy enforcement.

**Unknown.** Results are limited to the studied models, representation spaces, perturbations, and labeling method; implications for larger closed models and full agents are unresolved.

## 4. Defender-centric selection of jailbreak attacks

**Paper:** [How Jailbreak Attacks Inform Safety Alignment](https://arxiv.org/abs/2607.17152)  
**Submitted:** 2026-07-19  
**Stage:** Evaluation → Red teaming → Safety training

**Fact.** The paper proposes A-MESS and AttackSHAP to value jailbreak attacks by the downstream safety improvement they provide as training data, rather than by attack success rate alone. The authors report weak alignment between attack-success rankings and defender-centric utility in their evaluations.

**Why it matters.** A large attack collection can produce impressive red-team statistics without yielding the best training or mitigation set.

**Engineering interpretation.** Prioritize attack cases by control coverage, marginal safety value, and failure-mode diversity. Preserve a small, high-value regression set instead of optimizing only for attack count or ASR.

**Unknown.** The durability of selected subsets across model updates, domains, and adaptive attackers requires further evidence.

## 5. Salience attacks on multi-hop RAG agents

**Paper:** [Salience Induction against Multi-Hop RAG Agents: Threat and Defense](https://arxiv.org/abs/2607.17535)  
**Submitted:** 2026-07-20  
**Stage:** Retrieval → Context construction → Multi-hop reasoning

**Fact.** The paper introduces truth-preserving salience edits that change position, emphasis, framing, or semantic proximity without inserting false claims or instructions. The authors report 83.3% attack success under a 30% edit budget and reductions to 15.3% under standard attacks with their Salience Normalization defense.

**Why it matters.** Truthfulness checks and instruction filters can both pass while the evidence layout still redirects an agent’s reasoning.

**Engineering interpretation.** RAG defenses should test evidence ordering, decoy proximity, attribution binding, and robustness to context reformatting. Multi-hop answers should retain claim-to-source provenance.

**Unknown.** The benchmark’s transfer to production corpora, longer workflows, adaptive retrieval systems, and cost-sensitive deployments remains to be established.

## Cross-cutting insight

The five papers point to the same architectural gap: **model-visible context is often treated as both information and authority**. Stronger agent security requires enforcement outside free-form generation:

```text
provenance → capability boundary → context-bound authorization
           → validated action → authoritative readback
```

Input filtering remains useful, but it cannot replace execution policy, explicit authorization, and reconciliation.
